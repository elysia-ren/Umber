# Universal Embedded Model Runtime
## 可嵌入式统一 AI 模型运行时（初版）

---

> **历史存档**：本文件是 V0 架构总案的最初版本，已被
> [`V0-架构总案.md`](V0-架构总案.md) 取代。保留在这里只为记录设计演进过程，
> **不要把它当作当前设计**。

# 1. 项目定位

Universal Embedded Model Runtime 是一个：

> **随宿主软件一起分发、直接嵌入宿主进程的统一 AI 模型运行时组件。**

它解决的问题不是 Agent，也不是 AI Gateway，而是：

> **把不同 AI 厂商的 API、协议、模型信息、能力差异、流式行为、错误和凭据管理统一消化，让宿主软件只面对一套稳定的标准 API。**

典型关系：

```text
┌─────────────────────────────────────────────┐
│                 Host Application            │
│                                             │
│        Aine / Awen / Herta AI / ...         │
│                                             │
│   Editor / Agent / UI / Workflow / Plugin   │
│                    │                        │
│                    ▼                        │
│       ┌──────────────────────────────┐      │
│       │   Universal Model Runtime    │      │
│       │                              │      │
│       │  Canonical API               │      │
│       │  Invocation / Stream         │      │
│       │  Model Registry              │      │
│       │  Discovery / Metadata        │      │
│       │  Capability / Compatibility  │      │
│       │  Provider / Protocol Adapter  │      │
│       │  Retry / Timeout / Cancel    │      │
│       │  Credential Store             │      │
│       │  Embedded Runtime UI          │      │
│       └──────────────────────────────┘      │
│                    │                        │
└────────────────────┼────────────────────────┘
                     ▼
        OpenAI / Anthropic / Gemini /
        DeepSeek / Qwen / GLM / ...
```

每一个宿主软件各自携带一份 Runtime。

**不存在公共 Runtime 服务、localhost Gateway、中央模型代理，也不要求用户安装额外后台程序。**

Runtime 本质上是宿主软件里的一个基础组件。

# 2. 三条最高优先级原则

## 2.1 对外只有一套 Canonical API

无论底层连接：

```text
OpenAI Responses
OpenAI Chat Completions
Anthropic Messages
Google Gemini
DeepSeek
Qwen
第三方中转
企业 Gateway
本地模型
```

宿主只使用：

```text
generate()
stream()
cancel()
get_invocation()
models()
get_model()
embed()
```

Provider 差异不得泄漏到宿主业务层。

---

## 2.2 Provider 与 Protocol 必须解耦

Runtime 不采用：

```text
DeepSeek = DeepSeek Protocol
OpenAI = OpenAI Protocol
Qwen = Qwen Protocol
```

而采用：

```text
Provider
   │
   ├── Protocol A
   ├── Protocol B
   └── Protocol C
```

例如：

```text
DeepSeek
├── OpenAI Responses
├── OpenAI Chat
└── Anthropic Messages
```

而大量所谓：

```text
OpenAI Compatible
```

不创建新的协议类型，而统一视为：

```text
openai_chat
+
CompatibilityProfile
```

---

## 2.3 Runtime 不负责 Agent

Runtime 负责：

```text
统一模型调用
模型发现
模型信息
能力描述
兼容性判断
协议转换
流式事件
Invocation 生命周期
重试
超时
取消
错误
Usage
凭据
设置 UI
```

Runtime 不负责：

```text
Agent Loop
Memory
RAG
MCP
Skill
Planning
Workflow
Subagent
Prompt Library
自动 Agent Loop
自动多模型编排
```

Runtime 是：

> **模型基础设施，不是 Agent 框架。**

# 4. P0 核心协议

P0 只定义四种原生外部协议：

```text
openai_responses
openai_chat
anthropic_messages
gemini
```

另有：

```text
provider_native
```

作为厂商私有协议扩展槽。

但 `provider_native` 不是普通上层协议。

它只表示：

```text
某个 Provider 使用自己的私有通信协议
```

其实现最终仍必须转换成 Canonical API。

---

# 5. OpenAI Compatible 的正式定义

正式规则：

> **OpenAI Compatible 不是 ProtocolKind。**

所有 OpenAI Chat Completions 兼容服务：

```text
Provider
    ↓
CompatibilityProfile
    ↓
openai_chat Adapter
```

例如：

```text
DeepSeek
Qwen Gateway
企业中转
第三方 API
自建服务器
```

都可以：

```text
protocol = openai_chat
```

区别放进：

```text
CompatibilityProfile
```

而不是新增：

```text
deepseek_compatible
qwen_compatible
xxx_compatible
```

这样可以从根本上避免协议类型膨胀。

---

# 6. Provider 模型

Provider 表示：

> **提供模型服务的一方或一个服务身份。**

它不是通信协议。

P0 可以内置：

```text
OpenAI
Anthropic
Google
DeepSeek
```

以及：

```text
Custom
```

但这些都是：

> **Provider Preset / Provider Identity**

而不是代码级“必须存在的协议实现”。

例如：

```text
Provider = DeepSeek
Protocol = openai_responses
Endpoint = https://api.deepseek.com/v1
```

或者：

```text
Provider = DeepSeek
Protocol = anthropic_messages
Endpoint = https://api.deepseek.com
```

完全合法。

---

# 7. Provider Preset

Provider Preset 用于减少用户配置工作。

结构：

```text
ProviderPreset
├── id
├── display_name
├── protocols[]
├── default_endpoints[]
├── auth_definition
├── discovery_definition
└── catalog_hint
```

例如：

```text
DeepSeek
├── OpenAI Responses
│   └── https://api.deepseek.com/v1
├── OpenAI Chat
│   └── https://api.deepseek.com/v1
└── Anthropic
    └── https://api.deepseek.com
```

Preset 只是默认值。

**绝不锁死 Endpoint。**

---

# 8. Endpoint 与 Deployment

正式区分：

```text
Provider
    │
    ▼
Endpoint
    │
    ▼
Deployment
    │
    ▼
Model
```

其中：

### Provider

“谁提供服务”。

### Endpoint

“通过哪个地址连接”。

### Deployment

“这个 Endpoint 上具体暴露出的模型服务”。

### Model Identity

“它实际上是什么模型”。

因此不能简单把：

```text
deepseek-v4
```

当成完整模型对象。

---

# 9. Model Identity

统一模型身份：

```text
ModelIdentity
├── canonical_id
├── family
├── version
└── aliases[]
```

例如同一个底层模型可能：

```text
official/model-x
gateway/model-x
provider/model-x
```

但经过 Identity Resolution 后，可以知道它们可能对应同一个模型身份。

不过：

> **Identity 相同 ≠ Deployment 能力完全相同。**

因为不同 Endpoint 可能：

```text
支持能力不同
参数限制不同
上下文不同
价格不同
协议能力不同
```

所以必须保留 Deployment。

---

# 10. ModelInfo

`ModelInfo` 是 Runtime 对模型的标准知识描述。

建议结构：

```text
ModelInfo
├── identity
├── deployment
├── display_name
├── description
├── capabilities
├── limits
├── modalities
├── reasoning
├── tool_support
├── structured_output
├── pricing
├── compatibility
└── evidence[]
```

其中任何字段都不能假设：

> “官方写了支持，所以永远是真的。”

新增一个只面向开发阶段的工具：

```text
model-catalog-builder
```

它不随最终用户产品运行。

负责：

```text
采集
解析
标准化
Identity Matching
冲突检测
来源记录
数据校验
版本生成
```

输入可以来自：

```text
Models.dev
LiteLLM
OpenRouter
Provider Official Data
```

以及其他经过许可证审查、适合使用的数据源。

输出：

```text

```


才能工作。

# 13. 数据来源优先级

不把“某个数据库写了什么”直接当成真值。

建议按照：

```text
Provider 当前实际信息
        >
官方文档
        >
经过验证的 Bundled Catalog
        >
高质量第三方 Catalog
        >
Runtime Probe
        >
用户手动覆盖
```

但这里不是简单覆盖，而是：

> **按字段建立 Evidence。**

因为 Probe 对某些字段拥有比静态目录更高的事实价值，而官方文档对另一些字段又可能更可靠。

---

# 14. Evidence

每一个重要属性记录证据。

例如：

```text
context_window
value: 1000000

evidence:
- source: official
  confidence: 1.0
- source: models_dev
  confidence: 0.95
- source: litellm
  confidence: 0.95
```

或者：

```text
tool_call
value: supported

evidence:
- source: provider_api
- source: probe
  tested_at: ...
```

这样 Resolver 不是：

```text
A 覆盖 B
```

而是：

```text
A / B / C 发生冲突
        ↓
Evidence Resolution
        ↓
最终结论
+
冲突状态
```

状态：


# 16. CompatibilityProfile

尤其针对 OpenAI Compatible 服务。

统一记录：

```text
CompatibilityProfile
├── responses
├── chat
├── reasoning
├── tool_call
├── structured_output
├── multimodal
├── streaming
└── ...
```

每项：

```text
native
emulated
partial
unsupported
unknown
```

因此某个服务即使宣传：

> OpenAI Compatible

Runtime 也不会自动假定：

```text
100% Compatible
```

而是根据实际能力建立 Compatibility Profile。

# 17. Probe

Probe 正式分成两级。

## 17.1 Passive Probe

默认开启。

允许：

```text
GET /models
GET /model
HEAD
响应头解析
其他明确属于非生成性元数据请求
```

`OPTIONS` 为可选行为，不强制所有 Provider 执行。

核心契约：

```text
不得发送模型生成请求
不得调用 Tool
不得消耗模型 Token
```

不能承诺“远端服务器绝对没有任何副作用”，只保证 Runtime 不主动触发模型生成。

---

## 17.2 Active Probe

默认关闭。

需要用户明确启用：

```text
[ ] 主动检测模型能力
```

用于测试：

```text
Streaming
Tool Call
JSON / Structured Output
Vision
Reasoning
```

以及其他需要真实生成才能确认的能力。

因为主动 Probe 可能产生：

```text
Token 消耗
费用
Provider 请求额度
```

所以：

```text
默认关闭
```

探测结果持久缓存：

```text
ProbeResult
├── endpoint
├── model
├── test_type
├── result
├── tested_at
└── runtime_version
```

正常情况下不重复探测。

以下情况可以触发重新验证：

```text
用户手动刷新
Endpoint 发生变化
Model Deployment 发生变化
Runtime 明确判定原结果失效
```

因此是：

> **持久缓存，不是永久真值。**

---

# 18. Canonical Request

Runtime 不直接复制 OpenAI 或 Anthropic 的请求结构。

建立自己的：

```text
GenerateRequest
├── model
├── messages
├── tools
├── reasoning
├── generation
├── modalities
├── response_format
└── metadata
```

原则：

> **统一语义，不做最低公约数。**

即：

```text
可以表达主流模型真正具有的共同能力
```

而不是：

```text
为了兼容最弱 Provider
把整个 API 降级成最简单文本生成
```

---

# 19. Message

```text
Message
├── role
└── content[]
```

`role` 使用 Runtime 自身定义。

`content[]` 使用统一内容块：

```text
Text
Image
Audio
Video
ToolCall
ToolResult
Reasoning
```

因此不能出现：

```text
DeepSeekReasoningContent
AnthropicThinkingBlock
OpenAIResponseItem
```

这种 Provider 泄漏到 Canonical 层的类型。

---

# 20. Reasoning

Reasoning 是 Canonical Model/Event 语义的一部分。

Provider 侧：

```text
reasoning_content
thinking block
output reasoning
```

都转换成：

```text
Reasoning
ReasoningStarted
ReasoningDelta
ReasoningEnded
```

宿主无需知道具体厂商叫它：

```text
thinking
reasoning
reasoning_content
```

---

# 21. Tools

Canonical Tool：

```text
Tool
├── name
├── description
└── input_schema
```

模型产生：

```text
ToolCall
```

宿主执行后提交：

```text
ToolResult
```

Runtime 本身：

> **不负责执行 Tool。**

它只负责把模型请求和模型输出中的 Tool 语义统一传输。

这样 Agent / Host 可以自己决定：

```text
执行谁
怎么执行
是否允许
如何沙箱
```

---

# 22. Canonical Event

Runtime 内部和对外流式输出以事件为核心。

```text
ModelEvent
├── Started
├── ReasoningStarted
├── ReasoningDelta
├── ReasoningEnded
├── TextStarted
├── TextDelta
├── TextEnded
├── ToolCallStarted
├── ToolCallDelta
├── ToolCallFinished
├── UsageUpdated
├── Completed
└── Failed
```

统一原则：

> **所有 Delta 均为 append-only 增量。**

不是 replacement。

例如：

```text
TextDelta("你好")
TextDelta("，")
TextDelta("世界")
```

最终：

```text
你好，世界
```

---

# 23. Delta 的身份与顺序

为了保证并行 Tool Call 等场景不会产生歧义，每一个 Block / Tool Call 必须有明确归属。

例如：

```text
block_id
call_id
sequence
```

至少保证：

```text
谁的 Delta
当前属于哪个 Block
同一 Block 内的顺序
```

因此：

```text
Tool A delta
Tool B delta
Tool A delta
```

仍然可以无歧义重组。

`block-start` / `block-end` 保留。

上层可以：

```text
只消费 Delta
```

也可以：

```text
构造完整 Block
```

但两者的语义必须一致。

---

# 24. Invocation

每次模型调用拥有明确生命周期：

```text
Invocation
├── invocation_id
├── request
├── state
├── timestamps
└── cancellation
```

典型状态：

```text
Created
Running
Completed
Failed
Cancelled
```

因此：

```text
cancel(invocation_id)
```

不是“给 HTTP 请求发一个取消”。

它是：

> **取消一次 Runtime Invocation。**

底层是否能真正立即终止，由 Adapter / Transport 决定，但 Runtime 必须给上层一个一致的取消语义。

---

# 25. Generate 与 Stream

统一规定：

```text
generate(request)
```

本质上不是另外一套调用系统。

而是：

```text
stream(request)
    ↓
事件聚合
    ↓
Final Response
```

因此：

> **Runtime 内部以 Stream 为核心。**

这样可以避免：

```text
generate 一套逻辑
stream 一套逻辑
```

最后产生两套 Provider Adapter。

---

# 26. Canonical Error

宿主不应该判断：

```text
429
400
context_length_exceeded
insufficient_quota
```

统一成：

```text
ModelError
├── AuthenticationFailed
├── AuthorizationFailed
├── RateLimited
├── ContextExceeded
├── InvalidRequest
├── Unsupported
├── Timeout
├── NetworkError
├── ProviderError
├── EmptyResponse
├── Cancelled
└── Unknown
```

同时保留：

```text
provider_code
provider_message
raw_context
```

供日志和诊断。

---

# 27. Retryable 语义

`ModelError` 必须带：

```text
retryable: bool
```

典型：

```text
RateLimited        → true
Timeout            → true
NetworkError       → true
ProviderError(5xx) → true
```

典型：

```text
AuthenticationFailed → false
AuthorizationFailed  → false
ContextExceeded      → false
InvalidRequest       → false
Unsupported           → false
Cancelled             → false
```

`EmptyResponse` 不强制定性为永远不可重试，可以视 Provider 行为纳入可恢复错误。

但：

> **retryable = 允许 Runtime 考虑重试，不等于 Runtime 在任何情况下都必须重试。**

真正是否执行 Retry，还必须结合：

```text
Invocation 状态
请求是否已经产生部分输出
Provider 是否支持安全重放
剩余重试次数
Retry-After
```

尤其已经产生部分流式结果后，不能简单重新发送整次请求再把两个结果拼起来。

---

# 28. Retry

重试属于 Runtime Core，不属于 Provider Adapter。

Adapter 只负责：

```text
把 Canonical Request 转成 Provider Request
把 Provider Response 转成 Canonical Event
```

Runtime Core 负责：

```text
retry count
backoff
timeout
Retry-After
安全重放判断
```

上层无需判断：

```text
429 要不要重
500 要不要重
Timeout 要不要重
```

---

# 29. Timeout 与 Cancellation

同样属于 Runtime Core。

Provider Adapter 不自己发明一套：

```text
ProviderTimeout
ProviderCancel
```

而是 Runtime 定义统一生命周期。

因此：

```text
timeout
cancel
network interruption
```

最终都转换成统一 Invocation / ModelError 语义。

---

# 30. Credential Store

Credential 必须抽象为：

```text
CredentialStore
```

Core 不绑定操作系统。

实现可以是：

```text
Windows
→ Windows Credential Manager

macOS
→ Keychain

Linux
→ libsecret

Embedded Host
→ Host-provided secure storage
```

Core 只知道：

```text
get()
set()
delete()
exists()
```

API Key 不进入：

```text
普通配置 JSON
日志
模型 Catalog
Canonical Request
```

也不需要上传到我们的任何中央服务器。

---

# 31. Configuration

Provider 配置：

```text
ProviderConfiguration
├── provider
├── protocol
├── endpoint
├── credential_ref
├── discovery
├── compatibility
└── runtime_policy
```

用户配置流程：

```text

      ↓
选择 Protocol
      ↓

      ↓
填写 API Key
      ↓
测试连接
      ↓
发现模型
      ↓
建立 Deployment
      ↓
加载 ModelInfo
```

# 32. Endpoint 必须允许覆盖

例如：

```text
Provider:
DeepSeek

Protocol:
openai_responses

默认 Endpoint:
https://api.deepseek.com/v1
```

用户可以改成：

```text
https://my-gateway.example/v1
```

Runtime 应解释为：

```text
Provider Preset = DeepSeek
Endpoint = Custom
Protocol = openai_responses
```

而不是强制认为：

```text
DeepSeek = api.deepseek.com
```

因此原生支持：

```text
第三方中转
企业 Gateway
代理
区域 Endpoint
自建服务
```

# 33. Custom Provider 必须是一等公民

用户可以直接：

```text
Provider
→ Custom
```

然后填写：

```text
Name
Protocol
API URL
API Key
```

例如：

```text
My Gateway
openai_chat
https://example.com/v1
```

只要符合：

```text
openai_chat
```

就可以运行。

不要求 Runtime 事先知道：

```text

```

# 34. Model Discovery

已知 Provider：

```text

      ↓
默认 Endpoint
      ↓
Model Discovery
      ↓

```

Custom Provider：

```text

      ↓

      ↓
```


内部至少分成：


而不是：

```text

└── model_id = deepseek-v4

├── endpoint = gateway
```

二者可能：

```text

Limits 不同

```

# 39. 五个必须冻结的核心契约

V0 真正的开发入口不是继续增加 Provider，而是正式冻结这五个接口。

## 39.1 Canonical API Contract

定义：

```text
GenerateRequest
Message
Content
Tool
GenerateResponse
ModelEvent
Invocation
ModelError
Usage
```

核心保证：

> **所有 Provider 最终必须映射到这里。**

---

## 39.2 ModelInfo Contract

定义：

```text
ModelIdentity
Deployment
ModelInfo
Limit
Pricing
ReasoningInfo
Modalities
ToolSupport
Compatibility
Evidence
```

核心保证：

> **模型知识与具体网络协议解耦。**

---

## 39.3 CapabilityRecord Contract

定义：

```text
status
source
confidence
verified_at
```

核心保证：

> **能力不是一个未经解释的 Boolean。**

---

## 39.4 Provider Adapter Contract

Provider Adapter 应保持极小。

核心职责：

```text
describe()
discover_models()
execute()
```

必要时增加：

```text
prepare()
normalize_error()
```

但不允许把 Runtime Core 又塞进去。

Adapter 负责：

```text
协议转换
Provider 请求构造
Provider 响应解析
Provider 私有协议处理
```

Runtime Core 负责：

```text
Retry
Timeout
Cancel
Invocation
Stream
Error Policy
Usage
Capability
```

---

## 39.5 Runtime UI Contract

定义：

```text
show_provider_settings()
show_model_settings()
show_connection_test()
show_model_discovery()
```

UI 只负责：

```text
交互
展示
主题
本地化
```

核心配置和状态仍属于 Runtime Core。

---

# 40. Provider Adapter 的边界

Provider Adapter 内部允许存在：

```text
Provider-specific request
Provider-specific response
Provider-specific event mapping
Provider-specific error mapping
Provider-specific replay state
```

但这些东西：

> **不能进入 Canonical API。**

例如 Adapter 可以内部保存：

```text
AnthropicMessageState
OpenAIResponseState
GeminiPartState
```

这是允许的。

但是 Core 不得出现：

```text
AnthropicMessage
OpenAIResponseItem
GeminiPart
```

这种 Provider 类型。

# 41. Runtime API 示例

宿主看到的 API 尽量简单。

```rust
let models = runtime.models();

let request = GenerateRequest {
    model: model_id,
    messages,
    tools,
    reasoning,
    generation,
    modalities,
    response_format,
    metadata,
};

let mut stream = runtime.stream(request)?;

while let Some(event) = stream.next().await {
    match event {
        ModelEvent::TextDelta(delta) => {
            // append
        }

        ModelEvent::ReasoningDelta(delta) => {
            // append
        }

        ModelEvent::ToolCallDelta(delta) => {
            // reconstruct tool call
        }

        ModelEvent::Completed(response) => {
            // final response
        }

        ModelEvent::Failed(error) => {
            // unified error
        }

        _ => {}
    }
}
```

宿主不需要写：

```text
if provider == "deepseek"
if provider == "anthropic"
if response.reasoning_content...
if response.output_text...
```

否则说明 Runtime 边界已经失败。

# 51. Provider Adapter 最小接口

概念上：

```text
ProviderAdapter
├── describe()
├── discover_models()
└── execute()
```

其中：

### describe()

返回 Provider / Protocol 的能力与基础描述。

### discover_models()

负责：

```text
模型列表获取
模型 ID 解析
Provider 返回的基础元数据
```

### execute()

接受：

```text
Canonical Request
```

输出：

```text
Canonical Event
```

Adapter 不拥有：

```text
Retry policy
Credential policy
Invocation lifecycle
Capability resolver
Catalog
```

这些属于 Runtime。

```text

       │
       ├── Provider Preset
       ├── Protocol Registry
       └── Adapter Registry
```

因此未来添加 Provider 不意味着修改整个 Core。

# 53. Adding a new provider 的原则

例如新增：

```text

```

理想情况只是增加：

```text

```

如果协议已经是：

```text

```

甚至不需要新的 Protocol Adapter。

只有出现真正新的协议时才增加：

```text

```

如果只是：

```text
OpenAI Compatible
```

永远不能因此新增：

```text
mistral_compatible
```

这会成为架构失控的主要入口，因此正式禁止。

# 66. V0 冻结结论

到这里，V0 的核心不是“功能够不够多”，而是以下边界必须稳定：

```text
1. Canonical API
2. ModelInfo
3. CapabilityRecord
4. Provider Adapter Contract
5. Runtime UI Contract
```

以及以下铁律：

```text
Provider ≠ Protocol

OpenAI Compatible ≠ Protocol

provider_native = 扩展适配机制

Runtime ≠ Agent

Catalog ≠ Runtime Online Dependency

Passive Probe ≠ Generation

Active Probe = 用户主动开启

retryable ≠ 必然 retry

Delta = append-only

CredentialStore = 平台抽象

ModelIdentity ≠ Deployment

Capability ≠ Boolean

Adapter ≠ Runtime Core
```

这套规则冻结后，再开始实际编码。

后续新增 Provider、协议、模型数据、UI 页面，都必须服从这些边界，而不能反过来修改核心抽象。
