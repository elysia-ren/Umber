# Universal Embedded Model Runtime
## 可嵌入式统一 AI 模型运行时 · 架构总案（修订版）

---

> **修订版说明**（相对原版的变更）：
>
> 1. 取消 P0 / P1 分期，范围一次给全；仅保留"施工顺序"，它是工程实施次序，不构成范围分期。
> 2. 原"数据来源优先级"的线性列表改为**字段级优先级表**，消除与 Evidence 模型的自相矛盾。
> 3. 补全冻结契约缺口：`stop_reason`、`tool_choice`、缓存控制、结构化输出归一、部分结果交付、终结事件保证、四段超时、`ContentFiltered` / `Overloaded` 错误、Reasoning 透传与参数映射。
> 4. FFI 冻结为**拉取式 ABI**，明确所有权、panic、UTF-8、并发与版本协商。
> 5. Runtime UI 契约改为 **UISpec 数据契约 + 可替换参考实现**，使契约可冻结而视觉不冻结。
> 6. 新增**版本化契约**与 **Conformance Suite** 两个制度性契约。
> 7. 修正内部矛盾：主动 Probe 归属统一；Preset 示例改为反映厂商实际公开端点。

---

# 1. 项目定位

Universal Embedded Model Runtime 是一个：

> **随宿主软件一起分发、直接嵌入宿主进程的统一 AI 模型运行时组件。**

它解决的问题不是 Agent，也不是 AI Gateway，而是：

> **把不同 AI 厂商的 API、协议、模型信息、能力差异、流式行为、错误和凭据管理统一消化，让宿主软件只面对一套稳定的标准 API。**

典型关系：

```text
┌─────────────────────────────────────────────┐
│                 Host Application            │
│                                             │
│        Aine / Awen / Herta AI / ...         │
│                                             │
│   Editor / Agent / UI / Workflow / Plugin   │
│                    │                        │
│                    ▼                        │
│       ┌──────────────────────────────┐      │
│       │   Universal Model Runtime    │      │
│       │                              │      │
│       │  Canonical API               │      │
│       │  Invocation / Stream         │      │
│       │  Model Registry              │      │
│       │  Discovery / Metadata        │      │
│       │  Capability / Compatibility  │      │
│       │  Provider / Protocol Adapter │      │
│       │  Retry / Timeout / Cancel    │      │
│       │  Credential Store            │      │
│       │  Embedded Runtime UI         │      │
│       └──────────────────────────────┘      │
│                    │                        │
└────────────────────┼────────────────────────┘
                     ▼
        OpenAI / Anthropic / Gemini /
        DeepSeek / Qwen / GLM / ...
```

每一个宿主软件各自携带一份 Runtime。

**不存在公共 Runtime 服务、localhost Gateway、中央模型代理，也不要求用户安装额外后台程序。**

Runtime 本质上是宿主软件里的一个基础组件。

# 2. 三条最高优先级原则

## 2.1 对外只有一套 Canonical API

无论底层连接：

```text
OpenAI Responses
OpenAI Chat Completions
Anthropic Messages
Google Gemini
DeepSeek
Qwen
第三方中转
企业 Gateway
本地模型
```

宿主只使用：

```text
generate()
stream()
cancel()
get_invocation()
models()
get_model()
embed()
```

Provider 差异不得泄漏到宿主业务层。

---

## 2.2 Provider 与 Protocol 必须解耦

Runtime 不采用：

```text
DeepSeek = DeepSeek Protocol
OpenAI = OpenAI Protocol
Qwen = Qwen Protocol
```

而采用：

```text
Provider
   │
   ├── Protocol A
   ├── Protocol B
   └── Protocol C
```

例如：

```text
DeepSeek
├── OpenAI Chat
└── Anthropic Messages
```

而大量所谓：

```text
OpenAI Compatible
```

不创建新的协议类型，而统一视为：

```text
openai_chat
+
CompatibilityProfile
```

---

## 2.3 Runtime 不负责 Agent

Runtime 负责：

```text
统一模型调用
模型发现
模型信息
能力描述
兼容性判断
协议转换
流式事件
Invocation 生命周期
重试
超时
取消
错误
Usage
凭据
设置 UI
```

Runtime 不负责：

```text
Agent Loop
Memory
RAG
MCP
Skill
Planning
Workflow
Subagent
Prompt Library
自动 Agent Loop
自动多模型编排
```

Runtime 是：

> **模型基础设施，不是 Agent 框架。**

# 4. 核心协议

核心协议只定义四种原生外部协议：

```text
openai_responses
openai_chat
anthropic_messages
gemini
```

另有：

```text
provider_native
```

作为厂商私有协议扩展槽。

但 `provider_native` 不是普通上层协议。

它只表示：

```text
某个 Provider 使用自己的私有通信协议
```

其实现最终仍必须转换成 Canonical API。

# 5. OpenAI Compatible 的正式定义

正式规则：

> **OpenAI Compatible 不是 ProtocolKind。**

所有 OpenAI Chat Completions 兼容服务：

```text
Provider
    ↓
CompatibilityProfile
    ↓
openai_chat Adapter
```

例如：

```text
DeepSeek
Qwen Gateway
企业中转
第三方 API
自建服务器
```

都可以：

```text
protocol = openai_chat
```

区别放进：

```text
CompatibilityProfile
```

而不是新增：

```text
deepseek_compatible
qwen_compatible
xxx_compatible
```

这样可以从根本上避免协议类型膨胀。

# 6. Provider 模型

Provider 表示：

> **提供模型服务的一方或一个服务身份。**

它不是通信协议。

内置：

```text
OpenAI
Anthropic
Google
DeepSeek
Custom
```

但这些都是：

> **Provider Preset / Provider Identity**

而不是代码级"必须存在的协议实现"。

例如：

```text
Provider = DeepSeek
Protocol = openai_chat
Endpoint = https://api.deepseek.com/v1
```

或者：

```text
Provider = DeepSeek
Protocol = anthropic_messages
Endpoint = https://api.deepseek.com/anthropic
```

完全合法。

> **规则：任何 Provider × Protocol × Endpoint 的组合在架构上都是合法的；但 Preset 数据必须反映厂商当前实际公开提供的协议与端点。本文档中的示例只说明组合合法性，不构成 Preset 数据。**

# 7. Provider Preset

Provider Preset 用于减少用户配置工作。

结构：

```text
ProviderPreset
├── id
├── display_name
├── protocols[]
├── default_endpoints[]
├── auth_definition
├── discovery_definition
└── catalog_hint
```

例如（反映厂商当前实际公开端点）：

```text
DeepSeek
├── OpenAI Chat
│   └── https://api.deepseek.com/v1
└── Anthropic Messages
    └── https://api.deepseek.com/anthropic
```

Preset 只是默认值。

**绝不锁死 Endpoint。**

Preset 数据随 Catalog Builder 流水线一起校验与更新，端点以厂商实际公开文档为准。

# 8. Endpoint 与 Deployment

正式区分：

```text
Provider
    │
    ▼
Endpoint
    │
    ▼
Deployment
    │
    ▼
Model
```

其中：

### Provider

"谁提供服务"。

### Endpoint

"通过哪个地址连接"。

### Deployment

"这个 Endpoint 上具体暴露出的模型服务"。

### Model Identity

"它实际上是什么模型"。

因此不能简单把：

```text
deepseek-v4
```

当成完整模型对象。

---

# 9. Model Identity

统一模型身份：

```text
ModelIdentity
├── canonical_id
├── family
├── version
└── aliases[]
```

例如同一个底层模型可能：

```text
official/model-x
gateway/model-x
provider/model-x
```

但经过 Identity Resolution 后，可以知道它们可能对应同一个模型身份。

不过：

> **Identity 相同 ≠ Deployment 能力完全相同。**

因为不同 Endpoint 可能：

```text
支持能力不同
参数限制不同
上下文不同
价格不同
协议能力不同
```

所以必须保留 Deployment。

## 9.1 Identity Matching 的边界

身份匹配只做窄而可靠的事：

```text
├── 只在 Bundled Catalog 内进行
├── 只使用人工审核的 alias 表
├── 匹配前做规范化：小写、去组织前缀、去日期后缀
└── 不做运行时模糊合并
```

不确定时：

```text
保留为不同 Identity
+
标记 possible_match 供人工审核
```

理由：

> **错误的合并会污染能力与价格数据。宁可身份偏多，不可错误合并。**

# 12. Model Catalog Builder

一个只面向开发阶段的工具：

```text
model-catalog-builder
```

它不随最终用户产品运行。

负责：

```text
采集
解析
标准化
Identity Matching
冲突检测
来源记录
数据校验
版本生成
```

输入可以来自：

```text
Models.dev
LiteLLM
OpenRouter
Provider Official Data
```

以及其他经过许可证审查、适合使用的数据源。

输出：

```text
Canonical Model Catalog
```

再随 Runtime 一起分发。

```text
models.dev
LiteLLM
```

## 12.1 运作方式

```text
├── Catalog Builder 以 CI 流水线方式定期运行
├── 每次运行固定外部来源快照（可复现）
├── 输出 diff 进入人工审查后合入
├── 每个数据源维护一份许可证记录
└── Catalog 版本与来源快照一一对应
```

对任何第三方数据源：

> **仅使用许可证允许再利用和分发的内容，并保留来源、版本和许可信息。**

# 13. 字段级数据优先级

不存在全局线性优先级。

不同字段的事实价值属于不同来源，因此**按字段类别建立优先级表**：

```text
字段类别
├── 行为类
│   ├── 例子：tool_call / streaming / json_mode / vision 实测行为
│   └── 优先级：Runtime Probe(实测) > Provider API > 官方文档 > Catalog
│
├── 规格类
│   ├── 例子：context_window / max_output_tokens / modalities
│   └── 优先级：官方文档 > Provider API > Catalog > Probe(间接证据)
│
├── 价格类
│   ├── 例子：input / output 单价
│   └── 优先级：Provider API > 官方文档 > Catalog
│
└── 身份类
    ├── 例子：canonical_id / aliases / family
    └── 优先级：Catalog(人工审核) > Provider API
```

User Override 规则：

> **用户显式覆盖是该 Deployment 上的最终运行时值。**

但覆盖不破坏 Evidence 链：

```text
原始来源 + 冲突记录全部保留
source = user 单独标记
```

Resolver 算法（正式规则，保持简单可解释）：

```text
对每个字段：
1. 收集所有来源候选值 + Evidence
2. 用户显式覆盖存在 → 采用用户值，冲突记录保留
3. 否则 → 按字段类别优先级表取最高有效来源
4. 次高来源与结果冲突且差值显著 → 标记 conflict 状态
5. 输出 value + evidence[] + conflict?
```

> **confidence 只是来源先验，用于展示与排序，不参与自动加权仲裁。**

这样 Resolver 不是 `A 覆盖 B`，而是：

```text
A / B / C 发生冲突
        ↓
字段级优先级 + 冲突标记
        ↓
最终结论
+
冲突状态
```

# 14. Evidence

每一个重要属性记录证据。

例如：

```text
context_window
value: 1000000

evidence:
- source: official
  confidence: 1.0
- source: models_dev
  confidence: 0.95
- source: litellm
  confidence: 0.95
```

或者：

```text
tool_call
value: supported

evidence:
- source: provider_api
- source: probe
  tested_at: ...
```

其中：

> **confidence 是人工设定的每来源固定先验，不是动态计算值。**
> 它只用于展示与排序，不参与自动加权。

# 17. Probe

Probe 正式分成两级。

## 17.1 Passive Probe

默认开启。

允许：

```text
GET /models
GET /model
HEAD
响应头解析
其他明确属于非生成性元数据请求
```

`OPTIONS` 为可选行为，不强制所有 Provider 执行。

核心契约：

```text
不得发送模型生成请求
不得调用 Tool
不得消耗模型 Token
```

不能承诺"远端服务器绝对没有任何副作用"，只保证 Runtime 不主动触发模型生成。

---

## 17.2 Active Probe

**默认关闭。**

需要用户明确启用：

```text
[ ] 主动检测模型能力
```

用于测试：

```text
Streaming
Tool Call
JSON / Structured Output
Vision
Reasoning
```

以及其他需要真实生成才能确认的能力。

因为主动 Probe 可能产生：

```text
Token 消耗
费用
Provider 请求额度
```

所以：

```text
默认关闭
```

探测结果持久缓存：

```text
ProbeResult
├── endpoint
├── model
├── test_type
├── result
├── tested_at
└── runtime_version
```

正常情况下不重复探测。

以下情况可以触发重新验证：

```text
用户手动刷新
Endpoint 发生变化
Model Deployment 发生变化
Runtime 明确判定原结果失效
产生 ProbeResult 的 Runtime 主版本已变化
```

因此是：

> **持久缓存，不是永久真值。**

# 18. Canonical Request

Runtime 不直接复制 OpenAI 或 Anthropic 的请求结构。

建立自己的：

```text
GenerateRequest
├── model               // Deployment 引用
├── messages            // 见 §19
├── tools               // 见 §22
├── tool_choice         // 见 §22.1
├── reasoning           // 见 §21
├── generation          // max_output_tokens / temperature / top_p / stop / seed ...
├── modalities          // 输出模态声明
├── response_format     // 见 §18.1
├── caching             // 见 §20
└── metadata            // 宿主追踪与透传
```

原则：

> **统一语义，不做最低公约数。**

即：

```text
可以表达主流模型真正具有的共同能力
```

而不是：

```text
为了兼容最弱 Provider
把整个 API 降级成最简单文本生成
```

## 18.1 结构化输出归一

Canonical 使用 JSON Schema 方言：

```text
response_format
├── text
├── json_object
└── json_schema
```

各协议映射：

```text
├── OpenAI    → structured outputs / response_format.json_schema
├── Anthropic → 以内部合成 Tool 承载 schema（Adapter 自动处理）
├── Gemini    → responseSchema（子集映射，超集字段标记 Unsupported）
└── strict 语义差异、refusal 表现差异 → 写入 CompatibilityProfile
```

# 19. Message

```text
Message
├── role
└── content[]
```

`role` 使用 Runtime 自身定义。

`content[]` 使用统一内容块：

```text
Text
Image
Audio
Video
ToolCall
ToolResult
Reasoning
```

因此不能出现：

```text
DeepSeekReasoningContent
AnthropicThinkingBlock
OpenAIResponseItem
```

这种 Provider 泄漏到 Canonical 层的类型。

## 19.1 Reasoning 块的透传字段

```text
Reasoning
├── text
└── provider_payload    // 可选，opaque
```

规则：

> **`provider_payload` 由 Runtime 原样保存、原样回传，不解释、不修改。**

背景：部分 Provider 在多轮 Tool 调用中要求把先前的推理块（含签名或加密内容）原样回传，否则拒绝请求。

```text
宿主保留 provider_payload 回放历史
        → Adapter 原样映射回 Provider 格式

宿主丢弃 provider_payload
        → 合法
        → 但部分 Provider 可能拒绝多轮工具调用
        → 后果写入 CompatibilityProfile，由宿主知情决策
```

签名校验失败一律映射为 Canonical Error（InvalidRequest 类），并保留 provider 上下文。

# 20. 缓存控制

Prompt 缓存直接影响成本，因此是 Canonical 语义的一部分。

```text
内容块可携带 cache_control 标注
```

映射：

```text
├── Anthropic → 显式 cache_control 断点
├── OpenAI    → 自动缓存（无需标注，Runtime 不发多余字段）
└── Gemini    → 隐式缓存；显式 Context Cache 暂缓（见 §61）
```

缓存命中情况统一由回收：

```text
Usage.cached_input_tokens
```

# 21. Reasoning

Reasoning 是 Canonical Model/Event 语义的一部分。

## 21.1 请求侧：统一档位与映射

```text
reasoning
├── effort: minimal | low | medium | high
└── exclude: bool          // 不返回推理内容
```

Provider 映射表：

```text
├── OpenAI Responses  → reasoning.effort
├── OpenAI Chat       → reasoning_effort（支持时）
├── Anthropic         → thinking.type + budget_tokens 档位映射
└── Gemini            → thinkingBudget 档位映射
```

规则：

```text
Provider 不支持的档位就近降级
实际生效档位写入 CompatibilityProfile
```

## 21.2 响应侧：统一事件

Provider 侧：

```text
reasoning_content
thinking block
output reasoning
```

都转换成：

```text
Reasoning
ReasoningStarted
ReasoningDelta
ReasoningEnded
```

宿主无需知道具体厂商叫它：

```text
thinking
reasoning
reasoning_content
```

多轮回传规则见 §19.1。

# 22. Tools

Canonical Tool：

```text
Tool
├── name
├── description
└── input_schema
```

模型产生：

```text
ToolCall
```

宿主执行后提交：

```text
ToolResult
```

Runtime 本身：

> **不负责执行 Tool。**

它只负责把模型请求和模型输出中的 Tool 语义统一传输。

这样 Agent / Host 可以自己决定：

```text
执行谁
怎么执行
是否允许
如何沙箱
```

## 22.1 Tool Choice

```text
ToolChoice
├── auto
├── none
├── required
└── specific(name)
```

不支持 `required` / `specific` 的 Provider 由 Adapter 以提示词约束方式模拟：

```text
模拟成功 → 标记 emulated
无法保证 → 映射为 Unsupported 错误
```

---

# 23. Canonical Event

Runtime 内部和对外流式输出以事件为核心。

```text
ModelEvent
├── Started
├── ReasoningStarted
├── ReasoningDelta
├── ReasoningEnded
├── TextStarted
├── TextDelta
├── TextEnded
├── ToolCallStarted
├── ToolCallDelta
├── ToolCallFinished
├── UsageUpdated
├── Completed
├── Failed
└── Cancelled
```

统一原则：

> **所有 Delta 均为 append-only 增量。**

不是 replacement。

例如：

```text
TextDelta("你好")
TextDelta("，")
TextDelta("世界")
```

最终：

```text
你好，世界
```

## 23.1 终结事件保证

> **无论底层发生什么——正常结束、超时、取消、断流、畸形 SSE——每个 Invocation 恰好产生一个终结事件：Completed / Failed / Cancelled。**

```text
Provider 异常断流   → Runtime 合成 Failed
SSE 畸形无法解析    → Runtime 合成 Failed
用户取消           → Runtime 合成 Cancelled
正常结束           → Completed
```

宿主永远不需要自己猜测"流是不是死了"。

---

# 24. Delta 的身份与顺序

为了保证并行 Tool Call 等场景不会产生歧义，每一个 Block / Tool Call 必须有明确归属。

```text
block_id
call_id
sequence
```

补充正式规则：

> **同一 Invocation 内的所有事件共享一个全局单调递增 sequence。**

因此：

```text
事件全序确定
谁的 Delta 确定
当前属于哪个 Block 确定
同一 Block 内的顺序确定
```

```text
Tool A delta
Tool B delta
Tool A delta
```

仍然可以无歧义重组。

`block-start` / `block-end` 保留。

上层可以：

```text
只消费 Delta
```

也可以：

```text
构造完整 Block
```

但两者的语义必须一致。

---

# 25. Invocation

每次模型调用拥有明确生命周期：

```text
Invocation
├── invocation_id
├── request
├── state
├── timestamps        // created / started / ended
├── cancellation
└── partial()
```

状态：

```text
Created
Running
Completed
Failed
Cancelled
```

因此：

```text
cancel(invocation_id)
```

不是"给 HTTP 请求发一个取消"。

它是：

> **取消一次 Runtime Invocation。**

底层是否能真正立即终止，由 Adapter / Transport 决定，但 Runtime 必须给上层一个一致的取消语义。

## 25.1 部分结果保证

> **Invocation 进入 Failed 或 Cancelled 后，宿主必须仍能通过 `partial()` 取回已聚合的部分输出与已知 Usage。**

```text
partial()
├── 已聚合的 Text / Reasoning / ToolCall 内容块
├── 已知的 Usage（含中途 UsageUpdated）
└── 终结错误（如有）
```

Runtime 不得丢弃已产生的部分结果。

这也是 Retry 安全重放判断（§28）的输入。

---

# 26. Generate 与 Stream

统一规定：

```text
generate(request)
```

本质上不是另外一套调用系统。

而是：

```text
stream(request)
    ↓
事件聚合
    ↓
Final Response
```

因此：

> **Runtime 内部以 Stream 为核心。**

这样可以避免：

```text
generate 一套逻辑
stream 一套逻辑
```

最后产生两套 Provider Adapter。

## 26.1 等价性要求

部分 Provider 的流式 / 非流式端点在字段口径上存在差异（finish reason、usage 统计方式）。

正式规则：

```text
generate 必须经由 stream 聚合实现
每个协议的 Conformance fixtures 必须验证：
聚合结果与非流式端点语义一致（stop_reason / usage / tool call 完整性）
存在差异时，由 Adapter 显式修正并记录在案
```

---

# 27. Canonical Response

宿主拿到的最终响应不是裸文本。

```text
GenerateResponse
├── content[]              // 完整内容块（Text / Reasoning / ToolCall ...）
├── stop_reason
├── usage
├── provider_context       // 诊断用，见 §28
└── invocation_id
```

`stop_reason` 枚举：

```text
end_turn            // 自然结束
max_tokens          // 达到输出上限
tool_use            // 等待宿主执行工具
refusal             // 模型拒绝
safety_blocked      // 安全拦截
```

> **stop_reason 是宿主判断 Agent Loop 是否继续的唯一依据，任何协议必须映射到该枚举。**

---

# 28. Canonical Error

宿主不应该判断：

```text
429
400
context_length_exceeded
insufficient_quota
```

统一成：

```text
ModelError
├── AuthenticationFailed
├── AuthorizationFailed
├── RateLimited
├── Overloaded          // Provider 过载（如 529）
├── ContextExceeded
├── InvalidRequest
├── Unsupported
├── ContentFiltered     // 安全拦截 / 拒答
├── Timeout
├── NetworkError
├── ProviderError
├── EmptyResponse
├── Cancelled
└── Unknown
```

同时保留：

```text
provider_code
provider_message
raw_context
```

供日志和诊断。

规则：

> **`raw_context` 与一切 Runtime 日志在输出前必须经过凭据脱敏。**

---

# 29. Retryable 语义

`ModelError` 必须带：

```text
retryable: bool
```

典型：

```text
RateLimited         → true
Overloaded          → true
Timeout             → true
NetworkError        → true
ProviderError(5xx)  → true
```

典型：

```text
AuthenticationFailed → false
AuthorizationFailed  → false
ContextExceeded      → false
InvalidRequest       → false
Unsupported          → false
ContentFiltered      → false
Cancelled            → false
```

`EmptyResponse` 不强制定性为永远不可重试，可以视 Provider 行为纳入可恢复错误。

但：

> **retryable = 允许 Runtime 考虑重试，不等于 Runtime 在任何情况下都必须重试。**

真正是否执行 Retry，还必须结合：

```text
Invocation 状态
请求是否已经产生部分输出（见 §25.1）
Provider 是否支持安全重放
剩余重试次数
Retry-After
```

尤其已经产生部分流式结果后，不能简单重新发送整次请求再把两个结果拼起来。

---

# 30. Retry

重试属于 Runtime Core，不属于 Provider Adapter。

Adapter 只负责：

```text
把 Canonical Request 转成 Provider Request
把 Provider Response 转成 Canonical Event
```

Runtime Core 负责：

```text
retry count
backoff
timeout
Retry-After
安全重放判断
```

上层无需判断：

```text
429 要不要重
500 要不要重
Timeout 要不要重
```

---

# 31. Timeout 与 Cancellation

同样属于 Runtime Core。

Provider Adapter 不自己发明一套：

```text
ProviderTimeout
ProviderCancel
```

而是 Runtime 定义统一生命周期。

## 31.1 四段超时

单一总超时会误杀推理模型（首 token 可达分钟级），因此超时正式细分为四段：

```text
├── connect_timeout       // 建立连接
├── first_token_timeout   // 请求发出 → 首个事件（默认值必须宽松）
├── idle_timeout          // 流中相邻事件的最大间隔（stall 检测）
└── total_timeout         // 整个 Invocation 的可选上限
```

全部属于 Runtime Core，Adapter 不得私有实现。

## 31.2 统一收敛

```text
timeout
cancel
network interruption
畸形 SSE
```

最终都转换成统一 Invocation / ModelError 语义，并且都受 §23.1 终结事件保证约束。

# 32. Credential Store

Credential 必须抽象为：

```text
CredentialStore
```

Core 不绑定操作系统。

实现可以是：

```text
Windows
→ Windows Credential Manager

macOS
→ Keychain

Linux
→ libsecret

Embedded Host
→ Host-provided secure storage
```

Core 只知道：

```text
get()
set()
delete()
exists()
```

## 32.1 回退顺序

```text
宿主提供的实现
    ↓ 缺失时
操作系统 Keystore
    ↓ 缺失时
加密文件存储 + 明确的用户告警
```

API Key 不进入：

```text
普通配置 JSON
日志
模型 Catalog
Canonical Request
```

也不需要上传到我们的任何中央服务器。

# 34. Endpoint 必须允许覆盖

例如：

```text
Provider:
DeepSeek

Protocol:
openai_chat

默认 Endpoint:
https://api.deepseek.com/v1
```

用户可以改成：

```text
https://my-gateway.example/v1
```

Runtime 应解释为：

```text
Provider Preset = DeepSeek
Endpoint = Custom
Protocol = openai_chat
```

而不是强制认为：

```text
DeepSeek = api.deepseek.com
```

因此原生支持：

```text
第三方中转
企业 Gateway
代理
区域 Endpoint
自建服务
```

用户可以直接：

```text
Provider
→ Custom
```

然后填写：

```text
Name
Protocol

API Key
```

例如：

```text
My Gateway
openai_chat
https://example.com/v1
```

只要符合：

```text
openai_chat
```

就可以运行。

# 36. Model Discovery

已知 Provider：

```text
Provider Preset
      ↓
默认 Endpoint
      ↓
Model Discovery
      ↓
Model Registry
```

Custom Provider：

```text
用户填写 Endpoint
      ↓
选择 Protocol
      ↓
尝试 Discovery
      ↓
Model Registry
```

如果服务没有 Model List：

```text
自动发现失败
      ↓
允许手动添加 Model ID
```

所以：

> **没有 `/models` 不能成为使用模型的硬性阻断条件。**

# 37. Model Registry

内部至少分成：

```text
ModelIdentity
Deployment
ModelInfo
```

而不是：

```text
HashMap<String, Model>
```

例如：

```text
ModelIdentity
└── deepseek-v4

Deployment A
├── endpoint = official
├── protocol = openai_chat
└── model_id = deepseek-v4

Deployment B
├── endpoint = gateway
├── protocol = anthropic_messages
└── model_id = deepseek-v4
```

二者可能：

```text
Identity 相同
Capabilities 不同
Pricing 不同
Limits 不同
Compatibility 不同
```

# 38. Runtime UI：声明式契约 + 参考实现

正式决定：

> **Runtime Core 无 UI。UI 采用"声明式 UISpec 契约 + 可替换参考实现"双轨。**

## 38.1 UISpec 数据契约（冻结部分）

Core 暴露纯数据接口，宿主用任何技术渲染：

```text
settings_schema()        // 配置界面的声明式描述：字段、类型、校验、i18n key
apply_settings()         // 校验并应用
test_connection()        // 连接测试状态查询
discovery_session()      // 模型发现流程状态机
strings()                // 内置多语言文案
```

规则：

> **配置与状态的全部逻辑属于 Core；宿主渲染的只是 UISpec。**

因此任何宿主（原生 / Web / 脚本 UI）都能低成本获得完整设置功能。

## 38.2 参考实现（可替换部分）

随 Runtime 提供一套完整参考 UI：

```text
├── 接受 Theme / Language / Scale / Density
├── 覆盖 §59 的全部功能清单
└── 宿主可直接嵌入，也可仅作为 UISpec 的渲染对照
```

> **冻结的是 UISpec 数据契约；视觉与控件实现不是契约，可以随时替换。**

---

# 39. UI 与 Core 完全分离

Runtime Core：

```text
无 UI
```

Runtime UI（参考实现）：

```text
只调用 Core API / 只渲染 UISpec
```

因此：

```text
Aine
├── Runtime Core
└── Runtime UI（参考实现或自渲染）

Awen
├── Runtime Core
└── Runtime UI

Herta
├── Runtime Core
└── Runtime UI
```

完全复用。

---

# 40. UI 统一功能，不强制统一视觉

UISpec 渲染参数接受宿主：

```text
Theme
Language
Scale
Density
```

因此：

```text
Aine → 深色
Awen → 浅色
Herta → 自己的主题
```

但是 Provider / Model 管理逻辑完全一致。

这样既复用功能，又不会出现：

> "宿主软件突然弹出一个明显属于别的软件的设置窗口"。

# 41. 必须冻结的核心契约

真正的开发入口不是继续增加 Provider，而是正式冻结以下七个契约。

## 41.1 Canonical API Contract

定义：

```text
GenerateRequest        // 含 tool_choice / reasoning / caching / response_format
Message
Content
Tool / ToolChoice
GenerateResponse       // 含 stop_reason
ModelEvent             // 含终结事件保证
Invocation             // 含 partial()
ModelError             // 含 ContentFiltered / Overloaded
Usage
```

核心保证：

> **所有 Provider 最终必须映射到这里。**

---

## 41.2 ModelInfo Contract

定义：

```text
ModelIdentity
Deployment
ModelInfo
Limit
Pricing                // 含 effective_at，informational
ReasoningInfo
Modalities
ToolSupport
Compatibility
Evidence
```

核心保证：

> **模型知识与具体网络协议解耦。**

---

## 41.3 CapabilityRecord Contract

定义：

```text
status
source
confidence
verified_at
```

核心保证：

> **能力不是一个未经解释的 Boolean。**

---

## 41.4 Provider Adapter Contract

Provider Adapter 应保持极小。

核心职责：

```text
describe()
discover_models()
execute()
```

必要时增加：

```text
prepare()
normalize_error()
```

但不允许把 Runtime Core 又塞进去。

Adapter 负责：

```text
协议转换
Provider 请求构造
Provider 响应解析
Provider 私有协议处理
```

Runtime Core 负责：

```text
Retry
Timeout
Cancel
Invocation
Stream
Error Policy
Usage
Capability
```

---

## 41.5 Runtime UI Contract

冻结的是 UISpec 数据契约（见 §38.1）：

```text
settings_schema()
apply_settings()
test_connection()
discovery_session()
strings()
```

参考实现可替换，视觉不是契约。

---

## 41.6 FFI / ABI Contract

见 §50。核心点：

```text
拉取式流
句柄所有权规则
panic 不穿越边界
UTF-8 + 显式长度
并发 Invocation 合法
ABI 版本握手
```

---

## 41.7 Versioning Contract

见 §51。核心点：

```text
Runtime = semver，Canonical 契约变更 = 主版本
Catalog = 独立 format_version + 兼容区间
ABI = 独立 major + 握手校验
```

---

# 42. Provider Adapter 的边界

Provider Adapter 内部允许存在：

```text
Provider-specific request
Provider-specific response
Provider-specific event mapping
Provider-specific error mapping
Provider-specific replay state
```

但这些东西：

> **不能进入 Canonical API。**

例如 Adapter 可以内部保存：

```text
AnthropicMessageState
OpenAIResponseState
GeminiPartState
```

这是允许的。

但是 Core 不得出现：

```text
AnthropicMessage
OpenAIResponseItem
GeminiPart
```

这种 Provider 类型。

# 43. Runtime API 示例

宿主看到的 API 尽量简单。

```rust
let models = runtime.models();

let request = GenerateRequest {
    model: model_id,
    messages,
    tools,
    tool_choice: ToolChoice::Auto,
    reasoning: ReasoningConfig::default(),
    generation: GenerationConfig::default(),
    modalities,
    response_format: ResponseFormat::Text,
    caching: CachingConfig::default(),
    metadata,
};

let mut stream = runtime.stream(request)?;

while let Some(event) = stream.next().await {
    match event {
        ModelEvent::TextDelta(delta) => {
            // append
        }

        ModelEvent::ReasoningDelta(delta) => {
            // append
        }

        ModelEvent::ToolCallDelta(delta) => {
            // reconstruct tool call
        }

        ModelEvent::Completed(response) => {
            // final response，含 stop_reason
        }

        ModelEvent::Failed(error) => {
            // unified error；invocation.partial() 仍可取回部分结果
        }

        _ => {}
    }
}
```

宿主不需要写：

```text
if provider == "deepseek"
if provider == "anthropic"
if response.reasoning_content...
if response.output_text...
```

否则说明 Runtime 边界已经失败。

# 44. Embedding

Embedding 与生成属于同一 Runtime。

对外：

```text
embed(request)
```

但不要求：

```text
GenerateRequest
```

和：

```text
EmbeddingRequest
```

强行共用完全相同的数据结构。

共用的是：

```text
Runtime
Provider
Model Registry
Credential
Endpoint
Error
Usage
```

而不是强行把所有模型任务压成一个请求类型。

# 45. Usage

Runtime 对 Usage 建立统一结构：

```text
Usage
├── input_tokens
├── output_tokens
├── reasoning_tokens
├── cached_input_tokens
└── total_tokens
```

同时允许 Provider 返回的额外字段进入：

```text
provider_usage
```

但 Canonical API 只承诺统一字段。

这样既不丢信息，又不污染核心类型。

# 46. Pricing

Pricing 属于 Model Intelligence，不属于执行 Adapter。

因为：

```text
同一模型
+
不同 Endpoint
=
不同价格
```

因此价格应绑定到：

```text
Deployment / Model Endpoint
```

而不是简单绑定：

```text
ModelIdentity
```

并且价格必须拥有 Evidence。

正式结构：

```text
Pricing
├── currency
├── input_per_mtok
├── output_per_mtok
├── cached_input_per_mtok
├── effective_at
└── evidence[]
```

契约明示：

> **Pricing 是 informational 数据，随包分发必有滞后，不构成计费依据。成本估算由宿主自行基于 Usage × Pricing 完成。**

# 47. 本地 Catalog 与在线更新

Runtime 启动时：

```text
Bundled Catalog
      ↓
Local Catalog
```

联网后可以：

```text
检查更新
      ↓
下载增量 Catalog
      ↓
校验版本
      ↓
合并
```

但：

> **Runtime 即使完全离线，也必须能够正常运行。**

在线数据更新只是增强，不是运行前提。

# 48. User Override

用户可以手动覆盖：

```text
Model Name
Context Window
Capabilities
Pricing
Endpoint
Model ID
```

但不要直接把用户修改破坏原始 Evidence。

应记录：

```text
source = user
```

因此最终 Resolver 可以区分：

```text
官方说什么
目录说什么
Probe 测出什么
用户自己指定什么
```

# 50. FFI 与并发模型

第一阶段：

```text
Rust Core
      ↓
Stable C ABI
```

Rust 类型是内部唯一真值。

不要一开始分别维护：

```text
Rust schema
C schema
C++ schema
TypeScript schema
Python schema
```

否则非常容易产生多个互相漂移的协议。

后续绑定：

```text
Rust
 ↓
C ABI
 ↓
C/C++
Python
其他宿主语言
```

按需要生成。

## 50.1 ABI 形态（冻结）

C ABI 没有异步，因此流式采用**拉取式**：

```text
runtime_stream_next(handle, timeout_ms, out_event)
```

```text
├── 宿主线程主动拉取，阻塞等待 + 超时
├── Runtime 内部持有异步运行时，不向 ABI 暴露 future / async
└── 拉取期间取消通过 cancel(handle) 触发，next 返回 Cancelled 终结
```

## 50.2 ABI 硬规则

```text
├── 句柄式内存管理：create / retain / release 成对，谁分配谁释放逐条写明
├── panic 不得穿越边界：所有 ABI 入口 catch_unwind → 返回错误码
├── 字符串一律 UTF-8 + 显式长度，禁止依赖 C string 终止符的歧义语义
├── 线程安全：Runtime 句柄可跨线程共享；并发 Invocation 合法且互不阻塞
└── 所有入口对空句柄 / 错误状态返回确定性错误码，不 UB
```

## 50.3 ABI 版本协商

```text
runtime_abi_version() 握手
        ↓
主版本不兼容 → 初始化直接失败并返回原因
```

> **ABI 事后几乎不可修改，因此其形态属于"冻结前必须定"的最高优先级。**

# 51. 版本化契约

```text
├── Runtime：semver
│   └── Canonical 契约（§41.1）任何不兼容变更 = 主版本号递增
│
├── Catalog：独立 format_version
│   └── Runtime 声明支持的兼容区间 [min, max]，区间外拒绝加载并提示
│
├── C ABI：独立 major
│   └── FFI 握手校验（见 §50.3）
│
├── ProbeResult：记录产生时 runtime_version
│   └── 主版本变更列入重新验证条件（见 §17.2）
│
└── 宿主可查询：
    runtime.version()
    runtime.catalog_version()
    runtime.abi_version()
```

> **稳定契约的承诺必须靠版本策略兑现，而不是靠"我们不会改"的口头承诺。**

# 52. 一致性测试（Conformance）

本项目的价值主张是"稳定契约"。

因此 **Conformance Suite 是正式交付物，不是测试附赠品**。

```text
runtime-conformance/
├── fixtures/          # 每协议的 golden request / response / stream 序列
├── fake-providers/    # 可脚本化的假 Provider，供宿主集成测试
└── harness/           # 断言库：事件序列、错误映射、重放行为
```

规则：

> **每个协议 Adapter 必须通过对应 Conformance Suite 才能进入主干。这是唯一门票。**

fixtures 最低覆盖：

```text
├── 纯文本生成
├── 流式 Delta 重组（含并行 Block 归属）
├── 并行 Tool Call
├── Reasoning 输出与 provider_payload 回传
├── 结构化输出
├── 每类 ModelError 至少一例真实映射
├── 断流 / 畸形 SSE / 中途取消（终结事件保证）
├── 四段超时各一例
└── generate ≡ stream 聚合等价性
```

# 56. Adding a new provider 的原则

例如新增：

```text

```

理想情况只是增加：

```text
Provider Preset
```

如果协议已经是：

```text
openai_chat
```

甚至不需要新的 Protocol Adapter。

只有出现真正新的协议时才增加：

```text

```

如果只是：

```text

```

永远不能因此新增：

```text

```

这会成为架构失控的主要入口，因此正式禁止。

```text

Memory
```

# 67. 冻结结论

到这里，核心不是"功能够不够多"，而是以下边界必须稳定：

```text
1. Canonical API
2. ModelInfo
3. CapabilityRecord
4. Provider Adapter Contract
5. Runtime UI Contract（UISpec 数据契约）
6. FFI / ABI Contract
7. Versioning Contract
```

以及以下铁律：

```text
Provider ≠ Protocol

OpenAI Compatible ≠ Protocol

provider_native = 扩展适配机制

Runtime ≠ Agent

Catalog ≠ Runtime Online Dependency

Passive Probe ≠ Generation

Active Probe = 用户主动开启

retryable ≠ 必然 retry

Delta = append-only 且全局单调

每个 Invocation 恰好一个终结事件

失败 / 取消必可取回部分结果

stop_reason 是宿主判断循环的唯一依据

Reasoning.provider_payload = 原样透传

数据仲裁 = 字段级优先级，不是线性覆盖

Identity Matching = 人工审核精确匹配，不是模糊合并

CredentialStore = 平台抽象

ModelIdentity ≠ Deployment

Capability ≠ Boolean

Adapter ≠ Runtime Core

UI 契约 = UISpec 数据契约，视觉不是契约

Conformance = Adapter 进入主干的唯一门票

ABI 事后不可改，形态必须最先冻结
```

这套规则冻结后，再开始实际编码。

后续新增 Provider、协议、模型数据、UI 页面，都必须服从这些边界，而不能反过来修改核心抽象。

# 68. 施工顺序（不是分期）

> **以下是工程实施次序，不是范围分期。所有契约一次冻结，全部能力属于同一交付范围；顺序只反映依赖关系。**

```text
 1. 七大契约写成具体 schema 与类型定义（§41）
 2. runtime-core 骨架 + Conformance harness / fake-provider 先行
 3. openai_chat Adapter + fixtures          // 覆盖面最大，最先打通全链路
 4. anthropic_messages Adapter + fixtures   // 验证 Reasoning 透传 / 缓存标注
 5. openai_responses Adapter + fixtures     // 验证有状态推理项回传
 6. gemini Adapter + fixtures               // 结构差异最大，经验最足后做
 7. Model Intelligence：Registry / Resolver / Catalog 接入
 8. Probe：Passive 先行，Active 随后
 9. Catalog Builder CI 流水线
10. FFI 稳定化 + 参考实现 UI
```

每一步的完成标准都是同一条：

> **对应 Conformance Suite 全绿。**
